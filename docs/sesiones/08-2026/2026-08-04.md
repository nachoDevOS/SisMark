## Trabajo 1 — Las marcaciones dejan de tener eliminación lógica

**Commit:** `(pendiente de commit)` — mensaje sugerido: `perf(asistencias): quitar eliminación lógica y exigir motivo en la marcación manual`

### Problema

`asistencias` arrastraba `deleted_at`, `deleteUser_id` y `deleteObservacion`
porque el resto de las tablas del sistema los tiene. Pero una marcación no se da
de baja desde el sistema: entra del reloj o de un CSV y, si está mal, se corrige.
Nunca se usó una sola de esas tres columnas.

El costo sí era real: el `deleted_at IS NULL` que Eloquent agrega a cada consulta
le impide a MySQL usar la optimización de MIN/MAX sobre el índice, y la consulta
de «última marcación» del escritorio pasaba de 6 ms a 885 ms.

Aparte, la marcación manual (tipo `M`) es la única que no viene del reloj y se
guardaba sin ninguna explicación. En el informe procesado queda indistinguible de
una marcación real y no hay a quién preguntarle por qué se cargó.

### Archivos modificados

| Archivo | Cambio |
|---|---|
| `database/migrations/2026_07_24_022044_create_asistencias_table.php` | Fuera `softDeletes()`, `deleteUser_id` y `deleteObservacion` |
| `app/Models/Asistencia.php` | Fuera el trait `SoftDeletes` |
| `app/Traits/RegistersUserEvents.php` | El evento `deleting` solo escribe la auditoría de baja si el modelo usa `SoftDeletes` |
| `app/Http/Requests/StoreMarcacionRequest.php` | `observacion` obligatoria, mínimo 5 caracteres |
| `app/Http/Controllers/MarcacionController.php` | Guarda la observación al crear |
| `resources/views/components/modal-marcacion.blade.php` | Campo «Motivo» obligatorio en el modal |
| `app/Services/ResumenEscritorio.php` | Comentario de la consulta puesto al día |
| `app/Console/Commands/MigrarMarcacionesSia.php` | Comentario que aún nombraba `deleted_at` |
| `database/migrations/2026_08_04_133859_quitar_eliminacion_logica_de_asistencias.php` | **Nuevo** — da de baja las tres columnas en las bases ya creadas |

### Solución

El trait `RegistersUserEvents` es compartido por todos los modelos y escribía
`deleteUser_id` y `deleteObservacion` sin preguntar. En una tabla sin esas
columnas eso revienta con «Unknown column», así que ahora comprueba primero que
el modelo use `SoftDeletes`:

```php
if (! in_array(SoftDeletes::class, class_uses_recursive($model), true)) {
    return;
}
```

## Trabajo 2 — El listado de marcaciones tardaba ~14,5 s por página

**Commit:** `(pendiente de commit)` — mensaje sugerido: `perf(asistencias): filtrar por rango de fecha sin anular el índice`

### Problema

La pantalla de Marcaciones quedaba en «Cargando…». El filtro de fechas se armaba
así:

```php
->when($desde, fn ($query, $d) => $query->whereDate('fecha', '>=', $d))
->when($hasta, fn ($query, $h) => $query->whereDate('fecha', '<=', $h))
```

`whereDate()` genera `date(fecha) >= ?`. Envolver la columna en una función anula
el índice `(fecha, ci)` y MySQL recorre la tabla entera. Medido contra los datos
reales, con el rango por defecto (4 días):

| Consulta | Con `whereDate()` | Con rango |
|---|---|---|
| Página del listado | **8.652 ms** (recorre 4.153.400 filas) | **15,5 ms** (135 filas) |
| `count(*)` de la paginación | **5.871 ms** | **0,5 ms** |
| Total por carga | **~14,5 s** | **~16 ms** |

El `EXPLAIN` lo confirma: `key=NULL, rows=4153400` contra
`key=asistencias_fecha_ci_index, rows=135`.

Lo llamativo es que la regla ya estaba escrita en el sistema: el encabezado de
`app/Services/ResumenEscritorio.php` dice «**Nunca `whereDate()` sobre
`fecha`**». Estaba respetada en el escritorio y en ningún otro lado.

### Archivos modificados

| Archivo | Cambio |
|---|---|
| `app/Models/Asistencia.php` | Scope nuevo `enRango($desde, $hasta)` |
| `app/Http/Controllers/MarcacionController.php` | Listado y chequeo de duplicado |
| `app/Http/Controllers/PersonaController.php` | Solapa de marcaciones de la ficha y reporte imprimible |
| `app/Http/Controllers/ReporteMarcacionController.php` | Reporte «sin procesar» |
| `app/Services/ProcesadorAsistencia.php` | Marcas del rango del reporte procesado |
| `app/Services/RegistroAsistencia.php` | Chequeo de duplicado del import de CSV |
| `app/Services/ResumenEscritorio.php` | Su helper privado ahora delega en el scope |

### Solución

Un solo scope en el modelo, y todos los lugares que filtran por fecha pasan por
ahí:

```php
public function scopeEnRango(Builder $query, Carbon|string|null $desde, Carbon|string|null $hasta): Builder
{
    return $query
        ->when($desde !== null && $desde !== '',
            fn (Builder $sub) => $sub->where('fecha', '>=', Carbon::parse($desde)->startOfDay()))
        ->when($hasta !== null && $hasta !== '',
            fn (Builder $sub) => $sub->where('fecha', '<', Carbon::parse($hasta)->startOfDay()->addDay()));
}
```

El corte de arriba va por el **día siguiente** y no por `hasta 23:59:59`: así el
día `hasta` entra entero aunque alguna fila trajera hora.

Aparte, los dos chequeos de «esta marcación ya existe» (el de la marcación manual
y el de cada fila del CSV importado) comparaban `fecha` con `whereDate()`. Como
`fecha` siempre está guardada a medianoche —verificado: 0 filas de 4,4 millones
con hora distinta de `00:00:00`—, se comparan enteras y la búsqueda cae sobre el
índice único `(ci, fecha, hora)`. La `hora` sigue por `whereTime()`, porque hay
**539 filas viejas del SIA** con una fecha base distinta de `1899-12-30` y
compararla entera las dejaría pasar como si no existieran.


## Trabajo 3 — La columna «Funcionario» pedía un nombre por fila a Mamoré

**Commit:** `(pendiente de commit)` — mensaje sugerido: `perf(mamore): resolver los nombres del listado en paralelo`

### Problema

Arreglada la consulta, la pantalla seguía lenta. La columna «Funcionario» sale de
la API de Mamoré por cédula, y `ResolutorNombres` las pedía **una por una, en
serie**:

```php
foreach ($cis as $ci) {
    $ficha = $usarMamore ? $this->fichaMamore($ci) : null;   // una consulta HTTP por fila
```

Medido contra la API real, con la caché fría:

| Filas por página | Tiempo en resolver los nombres |
|---|---|
| 10 | **2.461 ms** |
| 50 | **9.218 ms** |

Son ~250 ms por viaje, uno atrás del otro. Con la caché tibia, 6 ms.

Y hay un límite duro que no estaba contemplado: la API responde
`X-RateLimit-Limit: 60` — **60 pedidos por minuto**, y 429 al pasarse. Una sola
pantalla de 100 filas con la caché fría se come la cuota entera y deja sin nombre
al resto del sistema.

### Archivos modificados

| Archivo | Cambio |
|---|---|
| `app/Services/MamoreClient.php` | `personasPorCi()`: varias cédulas en paralelo, de a 5 |
| `app/Services/ResolutorNombres.php` | Separa lo cacheado de lo faltante y pide el faltante en un solo pool |
| `tests/Feature/ResolutorNombresTest.php` | Nuevo, 5 pruebas |

### Solución

Las cédulas que ya están en caché salen de ahí; las que faltan se piden todas
juntas en un pool, con **cinco pedidos en vuelo** como techo para no vaciar la
cuota de golpe.

Cada cédula vuelve distinguiendo «no existe» de «no se pudo preguntar»:

```php
@return array<string, array{persona: ?array<string, mixed>, error: bool}>
```

Eso importa para la caché: un 404 se cachea por un día (Mamoré no tiene a esa
persona, y la ficha sale de la base local), pero un fallo transitorio —incluido
el 429 del límite— **no se cachea**, así se reintenta en la carga siguiente en
vez de dejar la fila sin nombre todo el día.

### Verificación

```
php artisan test --compact tests/Feature/ResolutorNombresTest.php
```

5 pruebas, 13 aserciones, todas pasan:

- resuelve todas las cédulas de la página en un solo pool;
- no vuelve a preguntar por las cédulas que ya están en caché;
- una cédula que Mamoré no tiene cae en la base local y no se vuelve a pedir;
- un fallo de la API no se cachea y se reintenta en la carga siguiente;
- sin Mamoré configurada resuelve todo desde la base local sin salir a la red.

### Pendiente — decisión

El paralelismo acota el daño pero no resuelve el fondo: **pedir el padrón fila
por fila no escala contra un límite de 60 pedidos por minuto**. El padrón de
Mamoré tiene 4.599 personas y el endpoint de listado devuelve como máximo 100 por
página (46 páginas, ~1,2 s cada una).

Dos caminos, a decidir:

- **Precargar el padrón a la caché una vez por día**, con un comando programado:
  46 pedidos, ~55 s, fuera de la pantalla. El listado sale siempre de caché,
  rápido y con el cargo. Necesita caché persistente (base o Redis) y que la tarea
  programada corra en el servidor.
- **Resolver los nombres del listado desde la base local** (`personas`), sin
  ninguna consulta HTTP. Instantáneo y sin cuota, pero la columna pierde el cargo
  —SIA no lo conoce—; quedaría solo el nombre.

**Primera parte — La pantalla de Marcaciones quedaba «Cargando…»**

Se reportó que la pantalla de Marcaciones tardaba demasiado en mostrar la
información. Se midió el comportamiento real contra la base de datos en uso y se

La primera: la forma en que el sistema pedía las marcaciones de un rango de

página se resuelve en **23 milésimas de segundo**.

La segunda: la columna que muestra el nombre y el cargo del funcionario consulta

la información aún no almacenada localmente, una pantalla de 50 filas demoraba
más de **9 segundos** solo en resolver los nombres. Ahora las consultas salen en
grupo, y se detectó además que ese sistema admite un máximo de 60 consultas por
minuto, lo que se tuvo en cuenta para no agotar el límite y dejar sin nombre al
resto del sistema.

**Segunda parte — Registro de marcaciones manuales**

Las marcaciones cargadas a mano son las únicas que no provienen del reloj
biométrico y hasta ahora se guardaban sin ninguna explicación, lo que las volvía
indistinguibles de una marcación real en los informes. A partir de este cambio el
sistema **exige indicar el motivo** (papeleta, olvido del funcionario, equipo
fuera de servicio) y lo conserva junto al registro.

En el mismo trabajo se retiró de la tabla de marcaciones el mecanismo de «baja
lógica», que no se usaba —una marcación no se da de baja, se corrige— y que
penalizaba el rendimiento de todas las consultas del módulo.

Las tres columnas del mecanismo retirado se dieron de baja de la base en la misma
jornada, previa verificación de que ninguno de los 4.413.951 registros tenía
información cargada en ellas. La operación tomó 32 segundos y no afectó los
datos: la tabla conserva sus 4.413.951 marcaciones.

**Punto que requiere definición**

Para que la consulta de nombres sea instantánea de manera permanente, se propone
traer una vez por día el padrón completo de funcionarios del sistema de Datos
Personales y conservarlo localmente, en lugar de consultarlo pantalla por
pantalla. La alternativa es mostrar en ese listado el nombre que ya guarda el
sistema propio, lo que sería inmediato pero dejaría la columna sin el cargo.
