## Trabajo 1 — Estado de aprobación de las licencias

**Commit:** `(pendiente)` — `feat(licencias): estado de aprobación (Pendiente/Aprobado/Rechazado)`

### Problema

Las licencias se cargan hoy por dos caminos —la copia del SIA y la carga a mano
de Recursos Humanos— y en los dos surten efecto apenas se registran. Para que el
funcionario pueda **solicitar** una licencia desde Mamoré hace falta un estado
intermedio: la solicitud tiene que existir sin justificar todavía la ausencia,
hasta que Recursos Humanos la apruebe o la rechace.

### Archivos modificados

| Archivo | Cambio |
|---|---|
| `database/migrations/2026_07_24_025819_create_licencias_table.php` | `estado` pasa de `smallInteger` a `string(12)`, con default `'Aprobado'`. |
| `database/factories/LicenciaFactory.php` | `'estado' => 'Aprobado'`. |
| `app/Services/ProcesadorAsistencia.php` | `licenciasDelRango()` filtra `where('estado', 'Aprobado')`. |
| `app/Http/Resources/LicenciaApiResource.php` | La API expone `estado`. |

### Solución

Se reusó la columna `estado` en vez de agregar una nueva. Venía del esquema del
SIA y **no la leía nadie**: el sistema jamás la consultaba y las **1.110.343**
licencias migradas estaban todas en `1`. No había ningún significado previo que
romper.

Se editó la migración original en lugar de agregar una que altere, porque la base
se va a levantar de cero.

**El default es `'Aprobado'`, no `'Pendiente'`.** Es lo que corresponde a lo que
ya existe: un millón de licencias históricas y todo lo que carga Recursos
Humanos. Además `MigrarLicenciasSia` no escribe esta columna y `estado` tampoco
está entre las columnas actualizables de su `upsert`, así que al reejecutar la
copia del SIA las filas nuevas entran aprobadas y las existentes conservan su
estado. `'Pendiente'` como default habría dejado sin efecto todo el histórico.

**El filtro en `ProcesadorAsistencia` es lo que hace que la columna signifique
algo.** Sin él, apenas un funcionario cargara una solicitud desde Mamoré esa
licencia ya le justificaría la ausencia, antes de que nadie la mirara: alcanzaría
con pedir una licencia para que el día dejara de contar como falta.

**Antes:**
```php
$table->smallInteger('estado')->default(1);   // nadie la leía

Licencia::query()->where('ci', $ci)           // sin filtro de estado
    ->whereDate('fecha', '>=', $desde)
```

**Después:**
```php
$table->string('estado', 12)->default('Aprobado');

Licencia::query()->where('ci', $ci)
    ->where('estado', 'Aprobado')             // solo las aprobadas justifican
    ->whereDate('fecha', '>=', $desde)
```

La API **no** filtra por estado: el funcionario tiene que ver en qué quedó lo que
pidió. El filtro es del cálculo de asistencia, no de la visibilidad.

```
→ 134 tests, 134 pasan
pint → passed
```

## Trabajo 2 — Endpoint para que el funcionario solicite su licencia

**Commit:** `(pendiente)` — `feat(api): solicitudes de licencia desde Mamoré, en estado Pendiente`

### Problema

Con el estado ya en la tabla, faltaba por dónde entra la solicitud: Mamoré
necesita una forma de anotar la licencia que pide el funcionario, sin que esa
solicitud surta efecto hasta que Recursos Humanos la revise.

### Archivos creados

| Archivo | Cambio |
|---|---|
| `app/Http/Controllers/Api/SolicitudLicenciaController.php` | `POST funcionarios/{ci}/licencias`, anota en «Pendiente». |

### Archivos modificados

| Archivo | Cambio |
|---|---|
| `app/Services/RegistroLicencia.php` | `anotar()` acepta `estado` (default `'Aprobado'`); `turnosDelRango()` se movió acá desde el controlador. |
| `app/Http/Controllers/LicenciaController.php` | Su `turnosDelRango()` delega en el servicio. |
| `routes/api.php` | La ruta nueva, primera de escritura de esta API. |

### Solución

El endpoint reusa `RegistroLicencia::anotar()`, el mismo servicio con el que
Recursos Humanos anota licencias desde la pantalla. Se le agregó el parámetro
`estado`, con default `'Aprobado'` para que el flujo existente no cambie en nada:
solo la API pide `'Pendiente'`.

**`estado` hay que escribirlo a mano en `$comunes`.** El servicio inserta con
`Licencia::insert()`, que no pasa por el modelo, así que el default de la columna
no se aplica: sin esto las solicitudes habrían entrado como aprobadas.

**`turnosDelRango()` se movió al servicio.** La usan ahora la pantalla y la API, y
su regla de solapamiento es sutil —la asignación sirve si empieza antes de que
termine el pedido y termina después de que empiece—; dos copias que se despeguen
licenciarían turnos distintos según por dónde entre la licencia.

El endpoint devuelve **422 con el motivo** cuando no hay nada que anotar: sin
turnos asignados en esas fechas no hay licencia posible, y si ya existe una para
ese día no se pisa. Ese texto es el que termina leyendo el funcionario en Mamoré.

**Antes:**
```php
// $comunes de anotar(): sin estado, el insert tomaba el default de la columna
'adjunto' => $datos['adjunto'] ?? null,
'adjuntoNombre' => $datos['adjuntoNombre'] ?? null,
```

**Después:**
```php
'adjunto' => $datos['adjunto'] ?? null,
'adjuntoNombre' => $datos['adjuntoNombre'] ?? null,
'estado' => $datos['estado'] ?? 'Aprobado',
```

### Verificación

De punta a punta desde Mamoré, contra esta base:

```
POST api/v1/funcionarios/7633685/licencias   → 201 «1 licencia(s) anotada(s).»

En licencias:  id=1110375  estado=Pendiente  turno_id=407  usuario=Ignacio
¿la toma el cálculo de asistencia?  NO — solo cuenta las aprobadas
```

```
php artisan test --filter="Licencia|Registro|Procesador|Api"
→ 134 tests, 134 pasan
pint → passed
```

### Nota de seguridad

Esta API era de **solo lectura** y ahora escribe. La clave compartida identifica
al sistema, no a la persona: con ella se podría solicitar una licencia a nombre
de cualquier cédula. Lo acota que la solicitud nazca «Pendiente» —una indebida no
puede justificar una ausencia sin que alguien de Recursos Humanos la mire—, y
queda anotado en la cabecera del controlador.

### Pendiente

**La pantalla de Recursos Humanos para aprobar o rechazar.** Hoy las solicitudes
quedan «Pendiente» y no hay cómo resolverlas desde la interfaz.

Siguen abiertas dos decisiones: si el funcionario puede volver a pedir tras un
rechazo —el índice único `(ci, fecha, turno_id)` lo bloquea— y si puede adjuntar
el respaldo desde Mamoré. `goceHaberes` se resolvió: la solicitud se anota con
goce y Recursos Humanos lo ajusta al aprobar.

## Trabajo 3 — La búsqueda de funcionarios perdía gente

**Commit:** `(pendiente)` — `fix(funcionarios): la búsqueda por varias palabras se delega a la API`

### Problema

Buscando **«maria rene»** el listado no encontraba a MARIA RENE TELLEZ ZABALA,
pero **«maria rene tellez»** sí. Había que agregar el apellido para dar con la
persona.

### Archivos modificados

| Archivo | Cambio |
|---|---|
| `app/Http/Controllers/PersonaController.php` | `funcionariosMamore()` deja de filtrar en memoria y delega la búsqueda entera a la API. |
| `tests/Feature/PersonaControllerTest.php` | El test que fijaba el filtrado local, reescrito; uno nuevo verifica que no se pida un lote grande. |

### Solución

La API de Mamoré solo sabía buscar una frase entera, y como el nombre está
partido en columnas (`first_name`, `middle_name`, …) ningún campo contiene «maria
rene» seguido: devolvía **0 resultados**.

Este controlador lo suplía con un rodeo: pedía **100 filas por la palabra más
larga** y cruzaba el resto en memoria. Ahí estaba la falla real —«maria» cruza
con **220 personas**, y las que caían después de la 100, ordenadas por apellido,
no aparecían nunca—. TELLEZ empieza con T, así que quedaba fuera del lote. Al
agregar «tellez» la palabra más larga pasaba a ser esa, que cruza con solo 5
personas, entraba en el lote y la encontraba.

La búsqueda se movió a donde están los datos: la API cruza cada palabra contra
todos los campos (ver el trabajo correspondiente en Mamoré) y este controlador le
pasa el texto tal cual.

**Antes:**
```php
$terminoMasLargo = collect($terminos)->sortByDesc(fn ($t) => mb_strlen($t))->first();
$respuesta = $mamore->people(1, 100, $terminoMasLargo, $contrato);  // ← el tope
$filtrados = collect(...)->filter(/* cruce en memoria */);
```

**Después:**
```php
$respuesta = $mamore->people($pagina, $porPagina, $busqueda, $contrato);
```

### Verificación

Contra la base real, la persona aparece en cualquier orden:

```
« maria rene »           LA ENCUENTRA      « tellez zabala »       LA ENCUENTRA
« maria tellez »         LA ENCUENTRA      « tellez zabala maria » LA ENCUENTRA
« rene tellez »          LA ENCUENTRA      « zabala tellez »       LA ENCUENTRA
```

Y funciona con quien no tiene segundo nombre ni apellido paterno:

```
PORFIDIO DACOSTA      « porfidio dacosta » / « dacosta porfidio »  LO ENCUENTRA
MIGUEL VARGAS LEIGUE  « miguel vargas »   / « vargas leigue miguel »  LO ENCUENTRA
```

## Informe para presentación (copiar/pegar en Word)

**Informe de trabajo — 15/08/2026**
**Responsable:** nachoDev

**Actividad:** Se preparó el sistema para que los funcionarios puedan solicitar
licencias y Recursos Humanos aprobarlas, y se corrigió la búsqueda de
funcionarios, que no encontraba a las personas.

**Problema detectado:**

Primero: las licencias solo podían registrarse ya otorgadas. No existía forma de
que un funcionario pidiera una y quedara esperando la revisión de Recursos
Humanos.

Segundo: al buscar un funcionario por su nombre, el sistema no lo encontraba. Por
ejemplo, escribiendo «maria rene» no aparecía María Rene Tellez; había que
escribir además el apellido. El motivo era que el sistema consultaba solo una
parte de las personas y descartaba el resto sin avisar.

**Solución aplicada:**

A las licencias se les agregó un estado: aprobada, pendiente o rechazada. Todas
las licencias que ya existían quedan como aprobadas, tal como estaban. Solo las
aprobadas justifican una ausencia, de modo que una solicitud sin revisar no puede
tapar una falta.

La búsqueda pasó a consultarse completa contra la base de datos de personal, con
todas las palabras escritas a la vez. Ahora encuentra a la persona en cualquier
orden: por nombre, por apellidos, o por ambos, y también a quienes no tienen
segundo nombre.

**Detalle de archivos modificados:**
1. Tabla de licencias: se agregó el estado de aprobación, con las licencias
   existentes marcadas como aprobadas.
2. Cálculo de asistencia: solo toma en cuenta las licencias aprobadas.
3. Listado de funcionarios: la búsqueda se resuelve contra la base completa en
   lugar de sobre un grupo reducido de personas.

**Resultado:** El sistema queda listo para recibir solicitudes de licencia con su
circuito de aprobación, y la búsqueda de funcionarios encuentra a la persona
escribiendo su nombre, sin necesidad de agregar el apellido.
